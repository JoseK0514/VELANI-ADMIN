## Retention and recovery

Prospects90days from original creation; edits/closure/reopen never reset it. Engaged business closure12calendar months; reopening before expiry requires new confirmed work. Case content unavailable at original source expiry (hub usually88days), internal transient case/notes purged by source+90days. Client/project/contact/note deletions cascade; cases unlink without extending source expiry. Holds apply only to reviewed internal business records, with a private reason/owner/review date; they never preserve a source request message. Expired review dates do not extend a hold. Audit and minimal command receipts365days; authentication/rate remnants expire separately.

Private holds, classifications, source reassignment or contact erasure require a reviewed operator SQL transaction; no public DELETE/merge/hold/reassignment route is provided. Holds must not promote an expired prospect or reset its original deadline. An expired object retained for review cannot be resurrected through a business command.

Deletion journal stores only entity type/UUID/time/sequence in the separate store. It is append-only to maintenance, read-only to web, and must outlive every restorable admin backup. No ordinary v1 procedure truncates it. Journal metadata lifecycle needs a separate reviewed archival decision; it is not a retained contact/message copy. Never restore both stores together or restore a backup older than the approved retention/restore coverage.

Web transactions take a shared journal lock and require journal maximum sequence=local applied watermark. Maintenance takes the exclusive lock, durably commits deletion intent first, deletes admin rows, then advances the watermark. Crash or restored older data fails closed until private reconciliation. Local tests verify crashes between intent and deletion, source expiry, reviewed holds, dependent-note cleanup and restoration with preserved external journal. Snapshot restore into a real hosted branch still needs explicit restore/delete approval and separate evidence.

Recovery of lost passkeys requires new session and auth-encryption roots in the approved secret store, plus both private owner-store targets. Recovery is `npm run operator -- recover-owner --environment ... --apply` after Jose's private provider-owner verification, using the existing pinned identity. It durably advances the independent authorization epoch and closes access, verifies both auth roots changed, increments generation, revokes sessions/keys, consumes pending challenges and opens a15-minute enrollment window. A new deployment must reference those rotated roots. Old server roots remain blocked. It does not rebind Google or trust an email message. No customer credential or employee sign-in behavior changes.

## Mandatory supported restore procedure

Every provider snapshot or logical/table restore starts with `npm run operator -- restore-begin --environment ... --apply`, using both private owner-store targets. Wait for recovery_pending success BEFORE restoring. This advances the non-restored authorization epoch and durably closes auth/business access, independent of the deletion watermark. Never restore the journal alongside the admin. Arbitrary owner-level SQL restores performed outside this procedure are not detected or qualified by the application; provider-owner access must follow this runbook.

Restore the admin while the fence remains pending. Run the private maintenance command with --reconcile-only to replay erasures. Rotate ADMIN_SESSION_KEY and ADMIN_AUTH_ENCRYPTION_KEY in the approved secret store; retain three distinct32-byte roots. `npm run operator -- restore-complete --environment ... --apply` checks private target bindings, schema owners, pending epoch, deletion reconciliation and changed auth-root fingerprints. It revokes every stored session/passkey, clears pending proofs, increments generation, opens a15-minute enrollment window and only then publishes the new epoch/fingerprints. Failure between stores leaves access closed. Deploy with the rotated roots; old deployments remain blocked. Jose must perform Google login and enroll two fresh factors before any business session is issued. Recheck guest/session/logout/UV/source/journal behavior before production. Clear UI pagination and pending edits after a restore; do not automatically replay pre-restore commands across the restored business timeline.

The journal web role can SELECT the authorization state but cannot change it. The scheduled deletion writer also cannot advance/reopen authorization. Only the private journal schema owner can perform this procedure. Owned regressions restore pre-logout and pre-recovery auth state with an unchanged deletion journal, verify closed access, refuse unchanged roots, and require fresh verified factors after recovery. This qualifies the supported procedure, not an unobserved hosted restore.
